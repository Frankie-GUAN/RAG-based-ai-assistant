## 0. 总原则

1. **检索质量优先。** 个人知识库的价值在检索，不在 Agent 编排。「从我的笔记里找到答案」是单步检索任务；ReAct 循环已建成并保留，但它的价值在于「模型自己决定要不要检索」，而不是让简单问题变慢。
2. **测量基线先行。** 伪造的相似度会污染喂给 LLM 的信号——基线不修好，后续优化全是自欺欺人。
3. **文档说真话。** 宣称 = 实现。做不到的从 README 删掉，做到了再写回去。
4. **降级优于失败。** 精排挂了退回 RRF、溯源解析不了就当没引用、答案出错时仍留下用户消息——增强功能永远不该拖垮主链路。

## 已交付：P0 检索质量与部署

### BM25 中文分词
`_tokenize` 从 `re.findall(r"[一-鿿]|...")` 换成 `jieba.lcut_for_search` + 小停用词表。搜索模式同时产出复合词与组成部分，既提高命中又不漏召回。

**连带修的**：pickle 里存的是**已分词**的语料，改分词器不会让旧索引失效、只会让它静默错配。因此新增 `rebuild_from_chroma()`（`python -m app.rag.bm25_index rebuild`），兑现了「BM25 索引是可重建的缓存」这句原本是空头支票的承诺。

### 真实相似度与稳定去重键
向量侧改用 `similarity_search_with_relevance_scores`。此前是 `1.0 - i * 0.05` 编出来的名次占位值，它一路流到工具输出里渲染成「相关度: 0.03」交给模型——模型读到低分会以为资料不相关而拒答。

去重键从 `page_content[:200]` 换成 `loader.py` 打的稳定 `chunk_id`（`来源#p页码#序号`）。用内容前缀会让同一文档开头相似的相邻分片被判成同一片段而互相覆盖。

### Reranker 接入
`settings.enable_reranker`（默认开）+ `settings.rerank_candidates`（默认 10）。两条硬约束：
- **失败降级**：模型缺失/加载失败时捕获异常并退回 RRF 顺序，检索照常工作；
- **只改顺序不改分数**：CrossEncoder logit 没有可解释量纲，当成「相关度」展示给模型会重演伪造分数那个错误。

模型加载失败进入 10 分钟冷却（沿用 `bm25_index` 的既有纪律），否则缺模型会让每条查询都平白卡几秒。

### Docker 与依赖
compose 此前把 `GEMINI_API_KEY` 传给读 `DEEPSEEK_API_KEY` 的后端——容器内必然拿不到 key；SerpAPI 未透传；模型无缓存卷；nginx 默认 60s 读超时切断长回答。依赖此前全是 `>=` 下限，两天内因此出了段错误与索引读不出来两次事故，现已全部钉死并与 Docker 镜像版本对齐。

## 已交付：P1 溯源与流式

### chat.py 重写（真流式 + 修复断链）
`chat.py` 调用的 `run_agent` 在 ReAct 改造后已不存在，**应用处于无法导入状态**。重写为转发 Agent 事件流：token 直接来自 `model.astream()`，删掉「全量返回后切 4 字符 + sleep 20ms」的假流式。同时删掉 `ChatRequest.has_docs`——ReAct 下由模型自主决定是否检索，客户端声明不再影响任何决策。

### 引用溯源
协议新增 `CitationEvent`，Agent Core 从 `search_documents` 结果里提取片段（去重、按 `search_documents` 过滤、载荷形状异常时不报错），在 `final` 之前外发；`chat.py` 落库到 `source_data` 并标记 `source_type="doc"`；会话接口把它解析回来，重开对话仍能看到依据；前端映射到早已存在却从未被喂过数据的 `SourcePanel`。

同时把 `metadata["source"]` 从绝对路径降级为文件名——它既是前端显示的来源标签，也是发给模型的上下文，绝对路径等于把自己的目录结构交给模型。

### 前端
按 `data.type` 分发（此前靠 payload 形状猜，`done` 帧里 `answer` 永远赢过 `route`，路由展示是死的）；`finally` 复位 `isStreaming`（此前任何异常都会让输入框永久禁用）；非 2xx 响应在进入 SSE 解析前就被挡下；错误展示到界面。

## P2（待排期）

### 滚动增量摘要（原 P0 计划 Task 9，规格现成）
窗口=10 时第 11 条消息触发摘要（只覆盖第 1 条），此后第 2..N-10 条既不在摘要也不在窗口，静默丢失；且 `_generate_summary` 的兜底文案会被永久钉死。需要 `summary_upto_message_id` 水位线列 + 幂等列检查（`create_all` 不 ALTER 已存在的表）。

### 知识库管理
删除文档（Chroma 与 BM25 双向清理）、重复上传去重、上传大小限制、`process_document` 移出事件循环（当前上传期间整个服务无响应）。

### 文档解析增强
